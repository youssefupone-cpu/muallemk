# API Keys يُرسل من الواجهة الأمامية — ثغرة أمان حرجة

- **التاريخ**: 2026-08-04
- **النوع**: bug (security)
- **الوضعية**: reviewer
- **الحالة**: open
- **الأولوية**: critical
- **الملفات المتأثرة**: `frontend/src/lib/api.ts`, `frontend/src/pages/SettingsPage.tsx`, `backend/.env.example:32`

## الوصف

تُرسل مفاتيح API (OpenAI، Anthropic، Tavily...) **من المتصفح مباشرة** إلى الخلفية بدلاً من أن تُخزن على الخادم. هذا يعني أن **أي API key يُدخله المستخدم يصبح مرئياً في Network Tab المتصفح** ويمكن لأي أحد يشارك الشاشة أو يثير devtools اقراصه.

## التأثير

- **استغلال تام**: أي كاشف devtools أو مشارك شاشة يمكنه سرقة جميع مفاتيح API لديك.
- **تعرض مستمر**: حتى في الإنتاج، إذا كان المستخدم يضغط F12، يرى المفتاح في Network → Payload.
- **لا يمكن إنقاصه**: المفتاح يمر عبر الشبكة كـ JSON — لا حتى HTTPS يحميه من أي كاشف بجانب الطريق.
- **Shared computer risk**: على أجهزة مشتركة، باقي المستخدمين يمكنهم استخراج المفاتيح.

## الحل المقترح

**استراتيجية: Backend-as-a-Reverse-Proxy** (ليست كـ proxy مرورياً، بل كـ proxy للكشف)

1. **لنقل الـ LLM**: استقبل `provider`، `model`، `temperature` من الواجهة، لكن **استخدم مفاتيح API المخزنة على الخادم** (من env/Secrets)، لا الخاصة بالمستخدم.
2. **للبروتوكول**: استقبل `api_key` في **header** (`X-Provider-Key`) وليس في body — يجعلها أقل وضوحاً في Network tab (headers مخفيّة جزئياً مقابل body).
3. **للكشف المتقدم**: استخدم **signed request** — الواجهة ترسل `provider=custom` + `model=gpt-4o`، والخلفية تستخدم `CUSTOM_OPENAI_BASE_URL` + `CUSTOM_OPENAI_API_KEY` المحددة في env.

```
✅ الحل المثالي:
  Frontend: { provider: "openai", model: "gpt-4o", temperature: 0.7 } (بدون api_key)
  Backend:  uses settings.OPENAI_API_KEY من env/secrets → calls OpenAI باسم المستخدم
```

## الحلول البديلة (مؤقتاً)

- **حد أدنى**: انتقل `api_key` من body إلى `Authorization: Bearer` header — يخفّر المظهر في Network tab.
- **متوسط**: شفّر api_key في الواجهة باستخدام `SubtleCrypto` وفك التشفير في الخلفية — لكن هذا لا يغيّر الأساس، فقط يُعقّد.
