# بطء توليد التقارير محلياً — غياب GPU وضغط ذاكرة

- **الحالة**: open
- **التاريخ**: 2026-08-02
- **النوع**: problems (قيود أجهزة تؤثر على E2E)
- **المشروع**: project3 — «معلّمك» (م9.3 تقارير AI)

## الوصف
توليد تقرير عبر `POST /plugins/reports/report` على هذا الجهاز يستغرق >10 دقائق
(جرّبنا انتظار 300s ثم 90s ثم 120s إضافية دون اكتمال؛ runner بقي نشطاً بـ 225% CPU).

## السبب الجذري (مُقاس)
- `size_vram: 0` — لا GPU إطلاقاً؛ كل التوليد على CPU
- الذاكرة 7.5GB شبه ممتلئة (MemAvailable انخفض إلى 164MB قبل التحرير) → ضغط swap
- عملية opencode نفسها تستهلك 100% من نواة (قياس: 28:12 CPU متراكمة)
- الباكند لا يمرر `num_predict` → النموذج الصغير يولّد بلا حد (2500+ رمز تقديرياً)

## القياسات (أوامر فعلية)
- `qwen3.5:0.8b` (جملة قصيرة، num_predict=30): HTTP 200 في 39.7s — **استجابة فارغة**، 2.4 tok/s
- `gemma3:1b-it-qat` (جملة قصيرة، num_predict=40): HTTP 200 في 36.7s — **نص عربي سليم**، 4.3 tok/s
- التقرير الكامل (بلا num_predict): >10 دقائق دون اكتمال (أُجهض بقتل الـ runner)

## الحل الجزئي المتاح
- استخدم `gemma3:1b-it-qat` كافتراضي للاختبار اليدوي (أسرع ويجيد العربية)
- التقرير الكامل يتطلب GPU أو تثبيت نموذج أكبر على جهاز أفضل

## الإصلاح المقترح (مستقبلاً)
- إضافة `num_predict` اختياري في `ReportRequest` (backend/app/plugins/report.py)
- تعيين حد افتراضي معقول (مثلاً 512) لمنع التوليد بلا سقف

## ما لا يعتبر خطأ
- الكود سليم: 68 اختباراً ناجحاً (تشمل 9 لمسار التقرير: توليد + حفظ + أخطاء)
- المسار يعمل: RAG query ناجح، التوليد الفعلي يعمل (جملة gemma)، الباكند يستجيب
