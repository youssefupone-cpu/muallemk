## 2. 🟠 مشاكل أمنية (4)

### 2.1 لا يوجد CORS في بيئة الإنتاج (Docker)

| | التفاصيل |
|---|---|
| **الملف | `backend/app/main.py:101-110` |
| **السلوك الفعلي** | `CORSMiddleware` يُضاف فقط إذا كانت `cors_origins` غير فارغة. في `config.py:47` القيمة الافتراضية هي `"http://localhost:3002,http://127.0.0.1:3002"` — إذًا يعمل محلياً. لكن `docker-compose.yml` يعمل الواجهة على المنفذ 80 عبر nginx، والخلفية على 8000 — **ولا يوجد CORS مضاف في الإنتاج**. الواجهة ستتفاعل مع `/api/` عبر nginx proxy، لذا الطلبات تمر عبر nginx إلى الخلفية — المتصفح قد يرفضها. |
| **الحل** | إما إزالة `/api/` proxy في nginx واستخدام `server_name` مباشرة، أو إضافة `http://localhost:80` إلى `cors_origins` في الإنتاج. البروكسي الحالي في nginx.conf يعيد كتابة `/api/` → `/`، مما يعني أن الواجهة تطلب `/api/chat` → nginx → `backend:8000/chat` — وهذا يعمل، لكن CORS غير مفعل في البناء الصريح. |

### تفصيل فجوة 3.4 — SSE Event Format (حرج)

الـ `chat/router.py` يستخدم `EventSourceResponse` مع `yield {"event": "message", "data": ...}`.
لكن `readSSE` في `api.ts:191-196` يقرأ `buffer.indexOf("\n")` ويفحص `line.startsWith("data: ")`.

**المشكلة**: `EventSourceResponse` يرسل تنسيق SSE كامل:
```
event: message
data: {"type": "conversation", "id": 1}

```
لكن `readSSE` لن يرى `data:` في البداية لأن السطر الأول هو `event: message`. لن يتم معالجة أي رسالة.

**الحل**: إما تعديل `readSSE` لمعالجة الـ `event:` field أو إزالته من `EventSourceResponse` (استخدام `event="message"` فقط). البروتوكول المقترح (`data: {...}` مباشرة) هو ما تتوقعه المكتبة.
